# GPT-Image-2 2K/4K 交付方案

更新时间：2026-06-17
适用范围：`D:\gpt_image_playground-main`

## 背景

当前产品里仍保留了 `1K / 2K / 4K` 档位、尺寸推导、计费档位和任务结果展示能力，但 `gpt-image-2` 公开可见的原生尺寸能力已经不适合继续按“直接原生输出 2K/4K”理解。

项目现状已经体现出这一收口：

- 前端尺寸面板会根据 `maxSupportedLongEdge` 动态隐藏 `2K / 4K`
- 前端提交前会按模型能力和长边限制自动压回可提交尺寸
- 服务端会按线路 `max_supported_long_edge` 过滤请求尺寸，不满足时直接判定为 `no_route`
- 后台准入规则明确要求只有真实探测达到 `2560 / 3840` 才能承诺 `2K / 4K`

因此，后续不应再把 `2K / 4K` 定义为“`gpt-image-2` 原生直出尺寸”，而应定义为“平台最终交付尺寸”。

## 目标

把当前产品中的 `2K / 4K` 从“上游原生尺寸承诺”改造为“平台交付规格承诺”。

最终效果：

- 用户仍然可以继续选择 `1K / 2K / 4K`
- `gpt-image-2` 仍然只负责生成其支持范围内的高质量底图
- 平台在服务端自动完成裁切、补边、超分和最终尺寸导出
- 用户收到的是符合目标像素尺寸的最终成品
- 前台和计费口径不再误导成“官方原生 2K/4K 直出”

## 产品定义调整

### 新定义

- `1K`：模型原生安全输出档位
- `2K`：平台增强交付档位
- `4K`：平台高清交付档位

### 不再使用的旧理解

- 不再把 `2K / 4K` 描述为 `gpt-image-2` 原生分辨率
- 不再把后台 `max_supported_long_edge` 直接等同于“是否能给用户交付 2K/4K”

### 对用户的解释口径

建议统一改成：

- `1K`：快速预览 / 原生底图
- `2K`：增强交付
- `4K`：高清交付

必要时补一句：

`2K / 4K` 为平台增强输出规格，系统会根据模型和线路能力自动完成底图生成与后处理。

## 总体链路

推荐把一次生成拆成两个阶段。

### 阶段 A：底图生成

输入：

- `modelSku`
- `prompt`
- `negativePrompt`
- `params.size`
- 参考图 / 遮罩

服务端内部行为：

1. 根据用户请求的目标尺寸，推导一个“底图策略”。
2. 选择最接近目标比例的原生底图尺寸。
3. 仍通过现有 `Image Gateway` 走 `gpt-image-2` 正常出图。

阶段 A 的产物：

- 一张或多张原生底图
- 每张底图的原始宽高
- 每张底图的实际使用参数

### 阶段 B：交付后处理

服务端内部行为：

1. 判断是否需要裁切。
2. 判断是否需要补边或扩图。
3. 判断是否需要超分。
4. 输出精确目标尺寸的最终交付图。

阶段 B 的产物：

- 一张或多张最终交付图
- 每张交付图的最终宽高
- 后处理链路摘要，例如 `crop + upscale`、`outpaint + upscale`

## 请求与数据模型

当前 `TaskParams.size` 直接承担“请求尺寸”语义，后续仍可保留，但要区分两个概念：

- `requested delivery size`：用户想要的最终交付尺寸
- `base generation size`：上游模型真正收到的底图尺寸

### 推荐做法

保留前台请求结构不大改，只扩展服务端内部语义。

前台仍发送：

```json
{
  "params": {
    "size": "3840x2160"
  }
}
```

服务端内部新增一层派生结构：

```json
{
  "deliveryTarget": {
    "size": "3840x2160",
    "tier": "4K",
    "ratio": "16:9"
  },
  "baseGeneration": {
    "size": "1536x1024",
    "ratio": "3:2"
  },
  "postProcessPlan": {
    "mode": "crop_then_upscale"
  }
}
```

### 不建议的做法

- 不建议把前台改成同时传 `base_size`
- 不建议要求用户自己理解“底图尺寸”和“交付尺寸”的区别
- 不建议把复杂后处理参数直接暴露给普通用户

## 底图策略

### 原则

优先保构图和比例，其次保像素。

也就是说，先挑最接近目标成品比例的 `gpt-image-2` 原生尺寸，再决定后续是裁切还是补边。

### 推荐映射

#### 方图

- `2048x2048` -> 底图 `1024x1024` -> `2x upscale`
- `4096x4096` -> 底图 `1024x1024` -> `4x upscale`

#### 横图

- `1920x1080` -> 底图 `1536x1024` -> 裁切到 `16:9` -> 缩放到 `1920x1080`
- `2560x1440` -> 底图 `1536x1024` -> 裁切或补边 -> 超分到 `2560x1440`
- `3840x2160` -> 底图 `1536x1024` -> 裁切或补边 -> 超分到 `3840x2160`

#### 竖图

- `1440x2560` -> 底图 `1024x1536` -> 裁切或补边 -> 超分
- `2160x3840` -> 底图 `1024x1536` -> 裁切或补边 -> 超分

### 比例决策规则

建议先按以下顺序匹配底图：

1. 目标比例接近 `1:1` -> 用 `1024x1024`
2. 目标比例明显偏横 -> 用 `1536x1024`
3. 目标比例明显偏竖 -> 用 `1024x1536`

如果误差较小，优先用更利于保主体的方向，而不是只看数学最接近。

## 后处理模式

### 模式 1：仅超分

适用：

- 方图
- 比例已经匹配
- 不需要改构图

优点：

- 最稳
- 最容易自动化
- 风险最低

### 模式 2：先裁切后超分

适用：

- 目标比例和原生底图接近
- 允许少量裁边

优点：

- 简单
- 输出稳定

风险：

- 可能裁掉边缘要素

### 模式 3：先补边后超分

适用：

- 不想裁掉主体
- 目标比例和底图差异较大
- 横幅、壁纸、视频封面等场景

优点：

- 对主体更友好

风险：

- 成本高于裁切
- 一致性要求更高

### 模式 4：拒绝交付

当出现以下情况时，服务端应直接失败，而不是静默降级：

- 没有可用底图线路
- 没有可用后处理能力
- 目标尺寸超出当前平台允许范围
- 多次后处理仍无法得到合格成品

## 后处理能力边界

### 平台能力分层

后续应把“线路生图能力”和“平台交付能力”拆成两层。

#### 层 1：底图生成能力

来自 `gateway_routes.max_supported_long_edge`。

它只回答：

- 这条线路原生能稳定返回多大底图

#### 层 2：交付能力

来自平台自己的后处理流水线能力。

它回答：

- 这个模型 SKU 最终能交付到什么尺寸档位

### 新的能力字段建议

对模型 SKU 聚合能力，建议新增：

- `maxBaseGenerationLongEdge`
- `maxDeliveryLongEdge`
- `deliveryModes`

示例：

```json
{
  "id": "gpt-image-2-fast",
  "supportedSizes": ["*"],
  "maxBaseGenerationLongEdge": 1536,
  "maxDeliveryLongEdge": 3840,
  "deliveryModes": ["upscale", "crop_then_upscale"]
}
```

这样前端以后开放 `2K/4K` 时，应优先看 `maxDeliveryLongEdge`，而不是继续直接看底图线路的 `max_supported_long_edge`。

## 服务端实现建议

### 推荐新增模块

- `server/src/imageDeliveryPlan.ts`
- `server/src/imagePostProcess.ts`
- `server/src/imageOutputMetadata.ts`

### 模块职责

#### `imageDeliveryPlan.ts`

负责：

- 根据请求尺寸推导目标档位
- 选择底图尺寸
- 决定后处理模式

输出一个结构化计划，例如：

```ts
type ImageDeliveryPlan = {
  requestedSize: string
  requestedTier: '1K' | '2K' | '4K'
  baseSize: string
  strategy: 'direct' | 'upscale' | 'crop_then_upscale' | 'pad_then_upscale'
}
```

#### `imagePostProcess.ts`

负责：

- 对底图做裁切
- 对底图做补边
- 对底图做超分
- 输出最终 data URL 或文件缓冲

第一版可以先实现：

- `direct`
- `upscale`
- `crop_then_upscale`

`pad_then_upscale` 可以放第二阶段。

#### `imageOutputMetadata.ts`

负责：

- 提取底图宽高
- 提取交付图宽高
- 生成结果说明
- 供任务结果页和后台任务详情复用

## 数据库扩展建议

当前 `generation_task_outputs` 已经具备：

- `width`
- `height`
- `revised_prompt`
- `raw_source_url`

这很好，说明当前结果表已经能承载“最终交付图”的物理信息。

但如果要把底图和交付图区分清楚，建议加一张子表，或者在当前表上补处理元数据。

### 方案 A：在现有输出表追加字段

可新增：

- `variant_role`：`base` / `final`
- `base_output_id`
- `requested_size`
- `actual_delivery_size`
- `base_generation_size`
- `delivery_strategy`

优点：

- 改动小
- 便于复用现有任务输出体系

缺点：

- 同一表会混合底图和最终图语义

### 方案 B：新增后处理结果表

新增例如：`generation_output_variants`

字段建议：

- `id`
- `task_id`
- `base_output_id`
- `variant_role`
- `storage_key`
- `public_url`
- `mime_type`
- `byte_size`
- `width`
- `height`
- `requested_size`
- `delivery_strategy`
- `created_at`

优点：

- 语义清晰
- 以后可扩展更多衍生版本

缺点：

- 实现量更大

### 当前推荐

第一阶段优先走方案 A。

原因：

- 当前项目已经有完整的 `generation_task_outputs`、分享、详情、后台列表链路
- 先把 `2K/4K` 交付跑通更重要
- 真正需要管理多变体时，再把结果结构升级为多变体表

## 任务状态建议

当前 `generation_tasks.status` 已支持：

- `queued`
- `running`
- `succeeded`
- `failed`
- `cancelled`
- `timeout`

建议不新增新的顶层状态，而是在 `running` 内部细分阶段。

### 内部阶段建议

- `base_generating`
- `post_processing`
- `persisting`

这些可以先只放进 `request_json` 或新的任务元数据字段里，不强制进正式枚举。

前端可显示为：

- `正在生成底图`
- `正在增强到 2K`
- `正在生成最终成片`

## 计费建议

### 原则

继续按“最终交付规格”计费，而不是按底图原生尺寸计费。

原因：

- 用户购买的是最终交付结果
- 平台的后处理也确实带来额外成本
- 现有产品档位已经是按 `1K / 2K / 4K` 组织

### 建议口径

- `1K`：按现有 `1` 点
- `2K`：按现有 `3` 点
- `4K`：按现有 `6` 点

### 成功判定

- 只有最终交付图成功产出，才按对应档位扣点
- 如果底图成功但后处理失败，则本次视为失败，不应按 `2K/4K` 收费
- 如果未来允许“降级交付”，则必须明确产品规则

### 不建议的默认行为

- 不建议底图成功但最终交付失败时仍按高档位收费
- 不建议无提示地把 `4K` 降成 `1K` 然后按 `4K` 收费

## 前端交互建议

### 尺寸面板

当前尺寸面板文案：

- `1K`：轻量预览
- `2K`：常规成片
- `4K`：高精输出

建议改成更准确的说法：

- `1K`：原生底图
- `2K`：增强交付
- `4K`：高清交付

### 任务详情

建议在详情里明确展示：

- 请求规格：`3840x2160`
- 底图规格：`1536x1024`
- 最终交付：`3840x2160`
- 处理方式：`裁切 + 超分`

### 输出告警

项目中已经有“实际输出低于请求尺寸”的告警逻辑。

后续改造后，应把这条告警改成更准确的判断：

- 如果最终交付图达到目标尺寸，不提示告警
- 如果最终交付图低于目标尺寸，才提示“未按交付规格返回”
- 不应仅因为底图小于请求尺寸就触发告警

## 后台与运营建议

### 后台模型能力展示

建议把模型能力拆成两栏：

- 原生底图能力
- 平台交付能力

例如：

- 原生底图：`1024x1024 / 1536x1024 / 1024x1536`
- 平台交付：`1K / 2K / 4K`

### 线路探测

现有高分探测主要验证“线路原生返回尺寸”。

后续应新增平台级验收：

- 验证底图是否能成功生成
- 验证后处理后是否能得到目标交付尺寸
- 验证最终结果像素是否达标

### 文档与客服口径

统一改成：

- `gpt-image-2` 负责底图生成
- 平台负责增强输出与最终交付规格

不要继续用“官方 2K / 4K 直出”描述。

## 第一阶段实施顺序

### 阶段 1：能力闭环

1. 增加交付计划模块。
2. 让 `2K / 4K` 请求先映射到底图尺寸。
3. 增加最小可用的超分与裁切后处理。
4. 把最终图存入现有输出表。
5. 以最终图尺寸作为任务结果显示依据。

### 阶段 2：体验完善

1. 任务详情展示底图与交付图信息。
2. 尺寸面板文案改成“增强交付”口径。
3. 增加后台交付能力展示。
4. 增加平台级 `2K / 4K` 验收脚本。

### 阶段 3：能力增强

1. 增加补边 / outpaint 模式。
2. 增加多变体输出管理。
3. 支持不同模型 SKU 使用不同交付策略。

## 当前推荐决策

如果要尽快恢复产品里的 `2K / 4K` 可用性，建议先做一个可控的第一阶段版本：

- 只支持 `1:1`、`16:9`、`9:16` 三类主流比例
- 只支持 `direct`、`upscale`、`crop_then_upscale`
- 先不做自动补边
- 先不新增复杂多变体表
- 继续沿用现有 `1 / 3 / 6` 点计费

这样可以用最小风险把“`2K / 4K` 作为平台交付能力”重新立起来。

## 结论

对当前项目来说，`2K / 4K` 的正确演进方向不是“恢复 `gpt-image-2` 原生直出大图”，而是：

1. 承认 `gpt-image-2` 主要负责原生底图生成。
2. 把 `2K / 4K` 改造成平台交付规格。
3. 在服务端补齐裁切、补边、超分等后处理链路。
4. 让前台、后台、计费、任务结果都围绕“最终交付尺寸”统一口径。

这条路线与当前项目已经存在的模型 SKU、尺寸档位、任务输出表、平台能力接口和后台线路管理结构是兼容的，能在现有架构上逐步落地，而不需要推翻现有网关体系。
